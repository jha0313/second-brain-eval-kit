0. TL;DR

  • 문제. Phase 1까지 brain은 사람마다 로컬 SQLite다. 각자 brain build와 첫 brain sync를 돌려야 하고, 각자 GitHub 토큰이 필요하다. 서비스 repo(비공개, PR 약 1,300개)는 첫 sync만 약 2,700번 호출한다. 사본마다 시점이 달라서 같은 질문에 사람마다 다른 답이 나온다.
  • Phase 2가 하는 일. brain의 진실을 Neon Postgres 하나로 옮긴다. 쓰기는 CI 한 곳만 한다. 사람이 수동으로 돌리는 workflow(workflow_dispatch)다. 사람과 에이전트는 SELECT만 되는 reader 연결로 같은 내용을 읽는다.
  • 데이터 모델. 파일·심볼·기억 항목마다 빌드가 바뀌어도 그대로인 id가 있다. 간선·링크·참조는 그 id를 가리킨다. 내용은 revision 행을 쌓기만 하고 덮어쓰지 않는다. 버전은 성공한 publish(run) 하나다. 기본 검색은 최신 run만 본다. --as-of run:42 | commit:<sha> | <날짜>를 주면 그때를 본다.
  • 읽는 길 둘. 기억 검색(search · get · source)은 서버에서 SQL 한 문장으로 끝낸다. 지도 명령(impact 등)은 노트북의 mirror(run 하나의 SQLite 사본)에서 Phase 0 코드로 돈다. mirror는 처음 한 번 전부 받고, 그 뒤에는 run 사이에 바뀐 행만 받는다. Neon Free의 월 5 GB 전송 한도 때문이다.
  • 안전. writer 비밀은 CI secret에만 있다. reader role은 DB가 쓰기를 거부한다. 마스킹과 인젝션 표시(Phase 1 §6.4–6.5)는 CI 안에서 업로드 전에 끝나고, 올리기 직전에 한 번 더 검사한다.

1.2 왜 지금인가

Phase 0의 로컬 빌드는 1분 안쪽이라 사람마다 돌려도 견딜 만했다. Phase 1이 GitHub 기억을 더하면서 사람마다 토큰과 긴 첫 sync가 필요해졌다. 팀이 brain을 같이 쓰려면 지금 한 곳으로 모아야 한다. 그래야 Phase 3에서 그 한 곳을 자동으로 갱신할 수 있다.

1.3 왜 서버 DB인가

대안무엇이 남나판단
CI가 SQLite 파일을 만들어 artifact나 release로 배포여전히 사람마다 파일 전체를 받는다. 파일을 통째로 바꾸므로 revision 이력이 없다. 권한은 파일을 받느냐 마느냐뿐이다. artifact 저장 용량은 GitHub 플랜 한도에 걸린다버림. Neon을 못 쓰게 되면 이 안으로 물러난다
공유 드라이브에 SQLite 하나여러 사람이 동시에 열면 잠금·손상 위험. 원격 파일 시스템에서 SQLite 잠금은 믿을 수 없다버림
Postgres (Neon)한 곳의 진실. DB 권한으로 쓰기를 막는다. revision 이력과 as-of 질의. Neon branch로 테스트를 production과 떼어 놓는다택함

성공 기준 (구현 후 확인). 모두 sandbox repo와 Neon test branch에서 잰다(§4).

  1. 불변식 테스트 V1–V23(§7.1)가 전부 통과한다.
  2. 지도 동등성. 같은 커밋에서 로컬 빌드 code.db와 mirror로 find · refs · impact · deps · why를 돌린 --json 결과가 의미상 같다. 비교에서 빼는 것은 시간(ms)과 freshness 줄뿐이다(§7.2).
  3. 기억 검색 동등성. 같은 커밋·같은 cursor에서 서버 search가 로컬 search보다 정답 키 기준 hit@3이 낮지 않다. 바뀐 케이스는 모두 목록으로 낸다(§7.3).
  4. 권한. reader로 직접 SQL을 보내 시도한 쓰기·DDL·임시 표가 전부 거부된다. writer는 DDL과 DELETE가 거부된다. 에이전트 환경에는 writer 비밀이 없다.
  5. 지연. 서울 노트북에서 search p95 1.5초 이하(compute가 깨어 있을 때, 30회). 잠든 compute의 첫 질의 5초 이하(5회). 실측값을 보고한다.
  6. 전송량. full mirror와 run 하나의 delta를 바이트로 잰다. 팀 10명, 월 90 run 기준 예상 월 전송량이 Free 한도(5 GB)의 50% 이하다.
  7. agent eval. skill-eval로 v2(로컬) 대 v3(서버)를 비교한다. A/A 쌍의 통과율 차이가 ±0.05 안일 때만 판정하고, v3 − v2의 95% CI 하한이 −0.10보다 크면 통과다.

3. 범위

한다.

  • codebase마다 Neon project 하나. 그 기본 branch가 production이다.
  • 스키마와 migration: 바뀌지 않는 id, revision, 유효 구간(valid_from · valid_to), 덮어쓰기 금지 trigger, role 셋.
  • publisher(CI): CI가 새로 만든 SQLite(code.db + github.db)를 기준 run의 mirror와 비교해, 바뀐 행만 한 트랜잭션으로 쓴다.
  • mirror: 서버의 run 하나를 SQLite 사본으로 받는다. 처음은 전부, 그 뒤는 delta만. CI는 mirror의 github.db로 Phase 1 sync를 그대로 돌리고, 노트북은 mirror의 code.db로 지도 명령을 돌린다.
  • brain CLI 서버 모드와 --as-of.
  • brain-publish workflow(수동)와 설치 문서.
  • 실제 질문과 키워드로 만든 eval 세트와 실행.

하지 않는다.

  • 자동 갱신(schedule, 스킬이 직접 dispatch). Phase 3에서 한다.
  • 로컬에서 production에 publish하기. publish는 workflow로만 한다. 수동 갱신은 Run workflow 버튼이다.
  • migration workflow. migration은 관리자가 owner URL로 직접 돌린다. 드물고, CI에 owner 비밀을 두지 않기 위해서다.
  • 사람마다 계정, SSO, 팀별 행 수준 권한(RLS). 한 codebase 안에서는 모두 같은 것을 읽는다.
  • 웹 UI, 임베딩, 여러 repo를 묶은 검색.
  • 옛 revision 정리(retention). 지금 규모에서는 필요 없다(§6.9).
  • vault(개인 Obsidian 노트). CI에는 vault가 없다. vault는 로컬 모드에서만 쓴다.
  • Neon IP Allow. Scale 플랜에만 있다.

가정과 확인한 사실:

  • Neon project. 사용자의 Neon project를 production으로 쓴다(Free 플랜, aws-us-west-2). 2026-11-16 그 project에서 직접 확인했다: PostgreSQL 18.7, 기본 branch 이름 production, DB neondb, collation · ctype C.UTF-8(builtin provider), 기본값 statement_timeout = 0 · idle_in_transaction_session_timeout = 5min · lock_timeout = 0. pg_trgm 1.6은 쓸 수 있고 아직 설치되지 않았다.
  • 한국어 trigram. 같은 locale(C.UTF-8, builtin)의 다른 Neon project(PostgreSQL 17.12)에서 확인했다(2026-11-16): show_trgm('크레딧 예약')이 trigram 7개, similarity('실행 전에 크레딧을 예약', '크레딧 예약') = 0.4, ILIKE '%크레딧%'이 맞는다. to_tsvector('simple', …)는 한국어를 공백으로만 자른다(크레딧을이 한 토큰). 그래서 한국어는 trigram이 맡는다. production에는 확장 설치 뒤 V14로 다시 확인한다.
  • Free 한도. project당 저장 1 GB, 월 100 CU-hour, branch 10개, 공개망 전송 월 5 GB. 전송 한도를 넘으면 다음 결제 주기까지 compute가 멈춘다. compute는 5분 쉬면 잠들고 끌 수 없다(Neon plans).
  • 비밀 위치. 연결 문자열은 저장소에 넣지 않는다. 노트북은 brain 자기 디렉터리의 .env.local(0600, gitignore. neon init이 쓰는 파일)이나 환경 변수에서 읽는다. CI는 Actions secret에서 읽는다. Neon API 키는 ~/.config/neon/에 둔다.
  • 규모: 지도 행 약 19만(노드 2.8만 + 간선 16만), 청크 5천, 링크 2.3만, 청크 본문 5.5 MB, PR·리뷰·댓글 수만 행.
  • 팀은 20명 이하다. reader 연결 수는 적다.
  • 서비스 repo는 이번 구현에서 건드리지 않는다(2026-11-16 결정). 그래서 workflow는 운영 repo 방식을 기본으로 만든다. 운영 repo(brain-ops)의 workflow가 서비스 repo main을 읽기 토큰으로 checkout하고 수집한다. writer 비밀은 운영 repo에만 있다. 서비스 repo 관리자가 직접 설치하는 방식은 문서로만 둔다. 구현 검증은 사용자 소유의 sandbox repo 두 개(소스 역할 · 운영 역할)와 Neon test branch로 한다. 서비스 repo 데이터를 production에 처음 publish하는 일은 읽기 토큰을 정한 뒤다(§9).

  • SQL로 만든 role은 neon_superuser에 들어가지 않고, 권한을 명시적으로 줘야 한다(Neon roles). 그래서 writer와 reader는 SQL로 만든다.
  • PUBLIC에서 걷어 낸다: REVOKE ALL ON SCHEMA brain FROM PUBLIC, REVOKE CREATE ON SCHEMA public FROM PUBLIC, REVOKE CREATE, TEMPORARY ON DATABASE neondb FROM PUBLIC. 기본값으로는 PUBLIC에 TEMPORARY가 있어서, reader가 읽기 전용을 끄면 임시 표를 만들 수 있다(PostgreSQL privileges). 앞으로 만들 표에도 같은 권한이 가도록 ALTER DEFAULT PRIVILEGES를 쓴다.
  • default_transaction_read_only는 세션이 끌 수 있다(PostgreSQL SET TRANSACTION). 막는 장치는 GRANT다. 읽기 전용 기본값은 실수를 줄이는 보조 장치다.
  • 변수 이름 (읽는 쪽은 reader만). brain CLI의 서버 모드는 BRAIN_READER_URL 하나만 읽는다: 환경 변수, 없으면 brain 자기 디렉터리의 .env.local에 있는 같은 이름. DATABASE_URL · DATABASE_URL_UNPOOLED(neon init이 쓰는 owner URL)는 어디서도 읽지 않는다. 관리자 노트북의 .env.local에 owner URL이 있어도 에이전트가 그 권한을 얻지 못한다. 연결한 뒤 첫 문장에서 current_user = 'brain_reader'이고 has_table_privilege(current_user, 'brain.run', 'INSERT')가 거짓인지 확인하고, 아니면 연결을 끊고 거부한다(exit 2, "reader 계정이 아닙니다"). 이어서 brain.binding의 소스 repo가 지금 checkout의 origin과 같은지 확인하고, 다르면 거부한다.
  • writer URL은 ci-publish만 BRAIN_WRITER_URL에서 읽는다. owner URL은 migrate만 명령행 인자로 받는다. 세 이름이 겹치지 않으므로 한 변수로 권한이 새지 않는다(V2에 "owner URL이 든 .env.local에서 서버 모드" 시나리오를 더한다).
  • reader 비밀이 새면: 누구든 brain을 읽을 수 있다(마스킹된 글과 지도). 쓰지는 못한다. ALTER ROLE brain_reader PASSWORD …로 바꾸고 팀에 새 URL을 돌린다. IP 제한은 Scale 플랜에만 있다.
  • writer 비밀의 경계: 운영 repo에 push할 수 있는 사람은 workflow를 고쳐 secret을 꺼낼 수 있다. 그래서 운영 repo의 쓰기 권한은 관리자만 갖는다. 서비스 repo에 쓰기 권한이 있는 사람과 에이전트는 운영 repo에 push할 수 없다.
  • fork에서 온 workflow에는 기본값으로 GITHUB_TOKEN 말고는 secret이 넘어가지 않는다(GitHub secrets). 비공개 repo에는 fork PR에 secret을 보내는 설정이 있다(GitHub Actions settings). 운영 repo에서는 그 설정을 끄고, brain-publish는 pull_request · pull_request_target으로 돌지 않는다.

덮어쓰기 금지 trigger.

  • revision·사실·기록 표에 BEFORE UPDATE OR DELETE: DELETE는 거부한다. UPDATE는 OLD.valid_to IS NULL이고 NEW.valid_to IS NOT NULL이며 나머지 열이 모두 같을 때만 허용한다. run · sync_state · identity 표는 UPDATE도 거부한다.
  • attempt: OLD.status = 'running'일 때만 끝 상태로 바꿀 수 있다. ok는 publish 트랜잭션 안에서만 된다(같은 트랜잭션이 run 행을 넣었을 때).
  • column 단위 GRANT와 겹치는 이중 장치다. owner의 실수도 막는다. 정리(retention)를 하게 되면 owner가 trigger를 잠시 끄는 migration으로만 한다.

R12COMMIT 응답을 못 받으면: 새 연결에서 같은 잠금을 쥔 뒤(lock_timeout = 60s) run에 내 attempt가 있는지 본다. 있으면 성공이다. 없으면 롤백된 것이고 R11로 간다. 잠금을 못 쥐면 결과를 "모름"으로 남기고 job을 실패로 끝낸다. 다시 쓰지 않는다원래 트랜잭션은 끝날 때까지 잠금을 쥔다. 잠금 없이 상태를 읽으면 커밋 중인 트랜잭션을 롤백으로 오판한다
R13첫 publish(서버가 빈 상태)는 행이 19만 개 넘게 들어간다. 1만 행 묶음으로 같은 트랜잭션 안에서 쓰고, 이때만 transaction_timeout을 10분으로 둔다평소 delta는 수천 행 이하라 수 초 안에 끝난다
R14migration이 CREATE EXTENSION pg_trgm을 하고, V14(한국어 trigram)를 production branch에서 바로 돌린다확인은 같은 locale의 다른 project에서 했다(§4). production에서 한 번 더 본다
R15sanitize 규칙이 바뀌면(sanitize_version 증가) 다음 publish는 --full이어야 한다(GitHub 전부 다시 받아 다시 정리). 이번 빌드가 다시 만들지 않는 현재 revision(빌드 창 5,000개 밖의 커밋 청크 등)은 CI가 mirror에서 읽어 새 규칙으로 다시 정리하고 새 revision으로 쓴다. 그래서 --full 뒤 현재 revision은 모두 새 sanitize_version이다(V20이 확인). 해시에 버전이 들어가므로 글이 있는 revision은 모두 새로 생긴다. 옛 revision은 그대로다. 옛 규칙이 놓친 비밀이 옛 revision에 있으면 owner가 그 행만 지우는 비상 migration을 쓴다(trigger를 잠시 끔)"덮어쓰지 않음"과 "새 비밀은 지워야 함"이 부딪히는 유일한 곳. 비상 절차로만 연다

6.6 안전 (Phase 1에서 이어짐)

  • 마스킹·정규화·인젝션 표시(Phase 1 §6.4–6.5)는 CI의 build·sync 안에서 끝난다. 올리기 직전에 R16이 delta 전체를 한 번 더 검사한다. 로그와 attempt.error에도 같은 검사를 한다.
  • 서버로 가는 것: 지도(경로 · 심볼 이름 · 줄 번호 · 간선), 문서·changes/·CHANGELOG 본문, 커밋 메시지, PR·이슈·리뷰·댓글 제목과 본문(마스킹됨), PR 변경 파일 목록, 참조. 소스 파일 본문은 가지 않는다. Phase 0 nodes에는 이름과 위치만 있고, chunks에는 마크다운과 커밋 메시지만 있다(src/db.mjs). 다만 마크다운과 토론 본문에는 코드 조각이 들어 있을 수 있다.
  • 읽기 출력은 Phase 1의 안전 렌더러와 인용 봉투를 그대로 쓴다. 서버 모드든 로컬 모드든 같은 코드다.
  • 에이전트가 인용 속 지시에 속아도 brain에 쓸 수 없다. reader 권한 밖이다. 이것이 "오염 방지"의 실제 장치다.

9. 열린 질문 (리뷰에서 정해 주세요)


  1. Launch로 옮길 때. Free로 정했습니다. 저장 · 월 CU-hour · 월 전송량 중 하나가 70%에 닿으면 Launch로 옮기는 것이 기본안입니다. production branch 보호(protected branch)도 Launch부터입니다.
  2. reader 계정. 기본안은 팀 공용 reader role 하나입니다. 사람마다 reader role을 주면 퇴사자만 끊을 수 있지만 관리할 것이 늘어납니다.
  3. 운영 repo. 기본안은 관리자만 쓰기 권한을 가진 운영 repo입니다. 서비스 repo 관리자가 직접 설치하길 원하면, environment secret(main에서만)과 main 보호 규칙이 되는 GitHub 플랜인지 먼저 봐야 합니다.
  4. 소스 읽기 토큰. 운영 repo가 서비스 repo를 읽으려면 토큰이 필요합니다(checkout과 API 수집 둘 다). 운영 repo의 GITHUB_TOKEN은 다른 비공개 repo를 읽지 못합니다(GitHub token). 선택지: GitHub App(서비스 repo 소유자가 설치, 읽기만), 또는 사람의 PAT(읽기 권한만 주는 fine-grained는 소유자가 개인 계정인 repo에 쓸 수 있는지 확인 필요, classic은 repo 전체라 범위가 넓음). 둘은 secret 모양이 다릅니다. PAT는 BRAIN_SOURCE_TOKEN에 그대로 둡니다. App은 App id와 private key를 secret에 두고 job마다 설치 토큰을 만듭니다(actions/create-github-app-token). 설치 토큰은 1시간 뒤 끝나므로(GitHub App token) 1시간을 넘는 bootstrap은 중간에 새로 만들어야 합니다. 첫 수집 약 2,700 호출은 PAT · App 한도(시간당 5,000) 안이라 한 job에 끝납니다. 정해지기 전에는 sandbox로만 검증합니다.
  5. 회사망에서 5432가 막히는 사람. 있으면 Neon serverless driver(HTTPS)를 읽기 전용 대체 경로로 넣습니다. 없으면 넣지 않습니다.




10. 한계


  • reader 비밀이 새면 brain 내용(마스킹된 글과 지도)을 누구든 읽을 수 있다. IP 제한은 Neon Scale 플랜에만 있다. 비밀 교체로 대응한다.
  • 운영 repo에 쓰기 권한이 있는 사람은 workflow를 고쳐 writer 비밀을 꺼낼 수 있다. 이 설계가 막는 것은 에이전트와 노트북, 서비스 repo 쪽의 쓰기다.
  • 마스킹이 놓친 비밀은 revision에 영원히 남는다. 지우려면 owner의 비상 migration(R15)이 필요하다. "덮어쓰지 않음"의 예외는 이것 하나다.
  • 첫 지도 명령은 mirror를 전부 받느라 느린 망에서 몇 초 걸린다. 그 뒤는 delta만 받는다.
  • Postgres FTS와 SQLite FTS5는 순위가 다르다. 기억 검색 결과 순서가 로컬과 다를 수 있다. eval로 재고, 지도 명령은 mirror라 같다.
  • Neon compute가 잠들어 있으면(Free는 5분 쉬면 잠들고 끌 수 없다) 첫 질의가 늦다. Neon은 깨는 데 보통 수백 ms라고 적는다(Neon connection latency). 연결 수립을 더한 실제 값은 잰다.
  • idle_in_transaction_session_timeout(5분)은 트랜잭션을 연 채 쉬는 세션만 끊는다. 트랜잭션 전체 시간은 transaction_timeout(R9)이 막는다. CI는 쓰기 직전에 새로 연결한다(R2).
  • 전송 한도(월 5 GB)를 넘으면 다음 주기까지 서버 읽기가 멈춘다. 그동안은 로컬 모드로 쓴다.
  • vault는 서버에 없다. 개인 노트는 로컬 모드에서만 본다.
  • 파일 이름이 바뀌면 identity가 끊긴다. 옛 경로의 기억은 --path 옛경로와 as-of로 찾는다.
