0. TL;DR

  • 문제. Phase 2의 brain은 사람이 workflow를 눌러야 갱신된다. 사람은 잊는다. 그러면 brain은 조용히 낡는다. 낡은 맥락은 모르는 것보다 나쁘다. 에이전트가 지난주의 코드와 기억을 근거로 자신 있게 틀린 답을 낸다.
  • Phase 3가 하는 일. brain-publish workflow를 매일 schedule과 workflow_dispatch로 돌린다. 지도는 매번 전부 다시 계산하고, DB에는 바뀐 행만 쓴다. 기억은 출처별 cursor 뒤만 가져온다. 쓰기는 한 트랜잭션이다. 어디서 실패하든 지도·기억·cursor가 함께 그대로 남는다.
  • 스킬이 스스로 갱신한다. 코드가 main과 다르거나 기억이 24시간보다 오래되면, brain이 workflow를 dispatch한다. 기다림은 90초 이하로 나눈다. 완료 조건은 셋이다. 서버의 최신 run 커밋 = 확인 시점의 main HEAD, 기억 cursor가 앞으로 감, 기억 나이 24시간 이내. 셋이 아니면 성공이라고 말하지 않는다.
  • 에이전트는 쓰지 못한다. dispatch는 입력이 없다. 에이전트의 토큰은 운영 repo의 Actions 권한만 있다. writer 비밀은 운영 repo에만 있고, 그 repo에는 관리자만 push한다.
  • 시간. trigger부터 published까지 p95 10분(SLO, hosted runner에서 잰다). 쓰기 트랜잭션은 60초에서 서버가 끊는다.

1. 왜 이 phase가 필요한가

1.1 낡은 brain이 하는 일

상황수동 갱신(Phase 2)에서 생기는 일
어제 머지된 PR이 함수 이름을 바꿈impact가 옛 이름의 호출처를 보여 준다. 새 호출처는 빠진다
리뷰어가 오늘 "이 방식은 접자"고 남김search가 그 리뷰를 못 찾는다. 에이전트는 접은 방식을 다시 제안한다
일주일 동안 아무도 publish를 안 누름답의 근거가 일주일 전 것이다. footer에 시각은 찍히지만 에이전트는 그 숫자를 근거로 행동하지 않는다
  • 서비스 repo는 최근 30일에 커밋 208개가 파일 3,076개를 건드렸다. 하루만 지나도 지도의 상당 부분이 바뀐다.
  • footer(Phase 1 §6.8)는 낡았다는 사실을 알려 줄 뿐이다. 고치는 사람이 없으면 매번 낡았다고 말만 한다.

1.2 왜 스킬이 직접 갱신을 요청하나

  • schedule만으로는 하루 사이의 변화를 놓친다. GitHub는 schedule을 늦추거나 빠뜨릴 수 있다고 적는다(GitHub events). schedule은 24시간을 보장하지 못한다.
  • 갱신이 필요한지 가장 먼저 아는 쪽은 답을 받는 에이전트다. 답의 footer에 run 커밋과 기억 시각이 있다.
  • 에이전트는 brain에 쓰지 않는다. 할 수 있는 것은 "CI야, 다시 만들어 줘"라는 요청뿐이다. 요청에는 내용을 바꾸는 입력이 없다. 그래서 Phase 2의 오염 방지(쓰기는 CI만)가 그대로 유지된다.

성공 기준 (구현 후 확인). 모두 sandbox repo와 Neon sandbox에서 잰다(§4).

  1. SLO. hosted runner에서 서비스 repo 크기(파일 약 4,600개)의 공개 코드로 dispatch 20회. trigger → published p95 10분 이하. 대기 시간과 실행 시간을 따로 내고, 10분을 넘긴 횟수를 센다.
  2. 롤백. 실패 주입(§7.2)의 기대는 셋으로 나뉜다. F1–F9 · F12 · F13: 도메인 표 전체(이력 포함)가 실패 전과 같다. F10 · F11 · F14(커밋은 됐는데 응답·후처리가 실패): 데이터는 그 publish 한 번만큼 들어가 있고 중복이 없으며 attempt는 ok다. F15(기준 run 경쟁): 먼저 커밋한 publish의 run만 남는다. 어느 경우든 그 뒤 정상 run 하나를 돌리면, 실패가 없었던 경우와 정규화 비교(§7)가 같다.
  3. 멱등. GitHub 응답을 고정하고 같은 커밋으로 두 번 돌면 두 번째는 새 행 0개다. 같은 Actions attempt를 두 번 보내면 두 번째는 쓰지 않는다.
  4. 스킬. 낡은 brain에서 질문한 agent trial이 갱신을 요청하고, 완료 조건 셋을 확인하고, 새 run의 footer로 답한다. 여러 에이전트가 동시에 낡음을 보면 dispatch는 최선의 노력으로 줄이고, 실제 publish는 한 번이다.
  5. 경계. 에이전트 토큰으로 운영 repo push · secret 읽기 · workflow 수정 · bootstrap 게이트 열기가 모두 거부된다. main이 아닌 ref, pull_request 이벤트로는 publish가 돌지 않는다.

3. 범위

한다.

  • brain-publish workflow에 schedule(하루 1회)을 더한다. concurrency, job 상한, 단계별 상한.
  • 출처별 cursor 규칙 정리와 CI 쪽 수집 상한.
  • publish를 시간 제한 아래에서 안전하게: 단계 감독(자식 프로세스), 늦은 연결, 연결 재시도, 트랜잭션 시간 제한, 신호 처리, COMMIT 응답 유실 처리.
  • 실행 상태와 낡음 판정, footer.
  • brain refresh: 낡음 판정 → 진행 중인 실행 확인 → dispatch → 나눠서 기다리기 → 완료 조건 확인.
  • SKILL.md 규칙: 낡으면 brain refresh 뒤에 답한다.
  • 실패 주입 훅과 테스트 하네스. SLO 측정.
  • 첫 수집 · --full용 관리자 workflow(brain-bootstrap).

하지 않는다.

  • push마다 갱신(§9 열린 질문 1). 지금은 schedule + 요청 dispatch.
  • 증분 지도 빌드. 지도는 매번 전부 다시 계산한다. 빌드가 2분 안쪽이라 증분의 버그 위험을 질 이유가 없다.
  • 실패한 실행의 부분 결과 쓰기(지도만 먼저 쓰기 등). 요구사항대로 전부 아니면 전무다.
  • 알림(Slack 등). 실패는 brain status와 footer, Actions 화면에 보인다.
  • abandoned를 정리하는 별도 job. abandoned는 읽을 때 Actions 상태로 판정해 보여 주기만 한다.
  • 로컬에서 production에 publish하기. Phase 2와 같다.
  • 서비스 repo 수정. 이번 구현은 sandbox repo에서 검증하고, 적용 방법을 문서로 남긴다(Phase 2 §4).

요청 원문(전사)이 설계의 해석
"메인 브랜치에 매일 스케줄해서 그런 dispatch를 만들어서"main에서 도는 workflow에 schedule(하루 1회)과 workflow_dispatch를 둘 다 건다
"지도는 매번 전체적으로 계산"brain build를 매 run 처음부터 돌린다 (Phase 2 R4 유지)

"cr에서 돌다 보면 1분이 넘어가잖아 … 타임아웃"CI job은 몇 분 걸린다. 두 쪽의 시간 제한을 설계한다. (1) CI 쪽: job · 단계 상한, 잠든 Neon compute, 긴 트랜잭션. (2) 에이전트 쪽: 에이전트의 명령 한 번은 보통 2분 안에 끝나야 한다. 그래서 기다림을 나눈다
"코드베이스 메모리 파트는 출처별로 커서"출처마다 cursor 하나: GitHub(서버 시각 T), git(마지막 run의 커밋). 그 뒤의 것만 새로 들어간다
"라이트가 실패하면 그래프랑 메모리랑 커서 다 같이 롤백"지도 delta, 기억 revision, cursor, run 행이 한 트랜잭션이다
"코드가 뒤쳐졌거나, 메모리가 24시간 이상 … 알아서 메인을 솔숲 출수를 해서"낡음이면 스킬이 workflow dispatch("솔숲 출수"는 "workflow dispatch"로 들었다)를 요청한다
"성공이랑 그런 것까지 다 확인을 해야지 완료"run 결론 success만으로는 완료가 아니다. 서버의 최신 run 커밋이 확인 시점의 main HEAD와 같고 기억 cursor가 새로워졌는지까지 본다
"푸시 한 번에 10분 안에 끝내야 된다"run 하나(trigger → published)가 10분 안. push마다 도는 trigger를 뜻했을 수도 있다(§9 열린 질문 1)

가정:

  • Phase 2의 publisher · mirror · 서버 읽기 · attempt / run 표가 있다.
  • workflow는 운영 repo 방식이다(Phase 2 §4). 운영 repo의 workflow가 소스 repo main을 소스 읽기 토큰으로 checkout하고 수집한다. writer 비밀은 운영 repo에만 있다.
  • Neon Free: compute는 5분 쉬면 잠들고 끌 수 없다(Neon scale to zero). 깨는 데 보통 수백 ms다(Neon connection latency).
  • 에이전트의 dispatch 토큰은 BRAIN_DISPATCH_TOKEN이다. fine-grained 토큰, 대상 repo는 운영 repo 하나, 권한은 Actions read · write(와 필수 Metadata read)뿐이다. dispatch API는 fine-grained 토큰에 Actions write를 요구한다(GitHub workflow dispatch). 개발자의 gh 로그인 토큰으로 대신하지 않는다.
  • 검증 환경: 사용자 소유의 sandbox repo 둘(소스 역할 · 운영 역할)과 Neon sandbox(production과 다른 project, 또는 test branch). 소스 역할 repo에는 서비스 repo와 크기가 비슷한 공개 TypeScript 코드를 넣는다. 서비스 repo의 코드는 넣지 않는다.

5.3 핵심 결정

결정이유버린 대안
하루 1회 schedule + 요청 dispatch요구사항. schedule은 "아무도 안 물어도 대개 하루 안"을, dispatch는 "물어본 순간에 최신"을 맡는다schedule만: 하루 안의 변화를 놓치고, schedule은 빠질 수 있다
schedule은 정각을 피한 시각(19:17 UTC = 04:17 KST)GitHub는 부하가 높을 때 schedule을 늦추거나 빠뜨릴 수 있다고 적는다. 정각은 흔히 몰리는 시간이다00:00 UTC
concurrency 그룹 하나, cancel-in-progress: false그룹에는 running 1개와 pending 1개만 있고, 새 pending이 오면 옛 pending은 취소된다(GitHub concurrency). 그룹 이름은 repo 전체에 걸리므로 다른 workflow가 같은 이름을 쓰지 않게 한다. 도는 publish를 끊지 않는다cancel-in-progress: true: 도는 publish가 계속 끊겨 영영 못 끝날 수 있다
줄 세우기는 concurrency, 마지막 울타리는 DB트랜잭션 안에서 최신 run이 기준 run이고, 새 커밋이 그 자손이고, 내 attempt가 running이어야 쓴다(Phase 2 R9–R10). 실패하면 다시 돌지 않는다실패 뒤 자동 재시도: 옛 checkout이 새 run 위에 쓸 수 있다
중복 dispatch는 job이 시작할 때 거른다dispatch API 호출 자체는 원자적으로 막을 수 없다. 대신 job이 시작하면 "최신 run이 같은 소스 커밋 · 같은 도구 버전이고, 그 run의 GitHub 수집이 내 run이 만들어진 뒤에 시작했나"를 본다(A5). 그러면 attempt를 skipped로 끝낸다중앙 조정자 서비스: 이 규모에 과하다
무거운 일은 트랜잭션 밖, 트랜잭션은 delta만빌드 · sync는 몇 분이다. 그동안 잠금 · 연결을 쥐면 시간 제한과 경쟁에 걸린다시작부터 끝까지 트랜잭션 하나
단계 상한은 감독 프로세스가 자식 프로세스를 끊어서 지킨다Phase 0 build는 동기 코드라 같은 프로세스 안의 시계로는 멈출 수 없다(src/build.mjs)같은 프로세스에서 시간 재기
트랜잭션 상한은 서버가 지킨다: transaction_timeout = 60sstatement_timeout은 문장 하나, idle_in_transaction_session_timeout은 쉬는 시간만 잰다(PostgreSQL client config). 트랜잭션 전체는 PostgreSQL 17부터 있는 transaction_timeout이 막는다클라이언트 시계만: 클라이언트가 멈추면 소용없다
스킬은 "요청"만 하고 완료는 서버 상태로 판정run 결론은 GitHub가 말하는 것이다. brain이 실제로 새로워졌는지는 서버의 run · sync_state가 말한다. 어떤 Actions run이 publish했는지는 상관없다내가 dispatch한 run의 결론만 확인: pending 교체 · 합쳐짐을 못 따라간다
기다림은 한 번에 90초 이하로 나누고, 이어 받기 상태는 파일에 둔다에이전트의 명령 한 번은 보통 2분 상한이 있다(Claude Code Bash 도구 기본값). 한 번에 10분을 기다리면 도구가 끊고, 에이전트는 실패로 읽는다brain refresh --wait 600 한 번
dispatch에는 입력이 없다. 에이전트 토큰은 운영 repo의 Actions 권한만에이전트가 넣을 수 있는 값이 없으면 내용을 오염시킬 길이 없다. 개발자의 넓은 토큰을 쓰면 workflow를 고칠 수 있다reason · ref 입력, gh auth token 재사용
첫 수집 · --full은 관리자 workflow로 따로약 2,700 호출은 GITHUB_TOKEN 한도(시간당 1,000)를 넘고 SLO와 job 상한 20분에 맞지 않는다. 소스 읽기 토큰(시간당 5,000)으로 한 job 안에서 끝낸다. 실패하면 처음부터 다시평소 workflow로 여러 번 나눠 돌기: 실패한 run은 아무것도 남기지 않아 이어 받을 수 없다

6.1 workflow

name: brain-publish
on:
  schedule:
    - cron: '17 19 * * *'              # 매일 19:17 UTC
  workflow_dispatch: {}                # 입력 없음
permissions:
  contents: read
  actions: read                        # 이 run의 created_at 읽기 (A5)
concurrency:
  group: brain-publish
  cancel-in-progress: false
env:
  BRAIN_SOURCE_REPO: owner/service     # 소스 repo. 입력으로 받지 않는다
  BRAIN_DIR: skills/codebase-brain     # 운영 repo 안의 brain 코드
jobs:
  publish:
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@<40자 SHA>      # 운영 repo: brain 코드와 workflow
        timeout-minutes: 1
        with:
          persist-credentials: false
      - uses: actions/checkout@<40자 SHA>      # 소스 repo main
        timeout-minutes: 2
        with:
          repository: ${{ env.BRAIN_SOURCE_REPO }}
          ref: main
          path: src-repo
          fetch-depth: 0
          token: ${{ secrets.BRAIN_SOURCE_TOKEN }}
          persist-credentials: false
      - uses: actions/setup-node@<40자 SHA>
        timeout-minutes: 1
        with:
          node-version: '22'
          cache: npm
          cache-dependency-path: ${{ env.BRAIN_DIR }}/package-lock.json
      - run: npm ci
        working-directory: ${{ env.BRAIN_DIR }}
        timeout-minutes: 2
      - uses: actions/cache/restore@<40자 SHA>
        timeout-minutes: 1
        with:
          path: .brain-mirror
          key: brain-mirror-${{ github.run_id }}-${{ github.run_attempt }}
          restore-keys: brain-mirror-
      # ci-publish runs build and sync as child processes WITHOUT BRAIN_WRITER_URL in their env, with
      # BRAIN_TYPESCRIPT=kit (never the source repo's typescript); only the parent opens the writer connection in S5
      - run: "$BRAIN_DIR/bin/brain ci-publish --source src-repo --mirror .brain-mirror"
        timeout-minutes: 12
        env:
          BRAIN_TYPESCRIPT: kit
          BRAIN_WRITER_URL: ${{ secrets.BRAIN_WRITER_URL }}
          BRAIN_SOURCE_TOKEN: ${{ secrets.BRAIN_SOURCE_TOKEN }}
          GITHUB_TOKEN: ${{ github.token }}        # A5: 이 run의 created_at만 읽는다
          GHA_RUN_ID: ${{ github.run_id }}
          GHA_RUN_ATTEMPT: ${{ github.run_attempt }}
      - uses: actions/cache/save@<40자 SHA>
        if: success()
        timeout-minutes: 1
        with:
          path: .brain-mirror
          key: brain-mirror-${{ github.run_id }}-${{ github.run_attempt }}
  • schedule은 기본 브랜치에서만 돈다. workflow_dispatch는 workflow 파일이 기본 브랜치에 있어야 하고, API로 다른 ref에도 보낼 수 있다(GitHub events). 그래서 if: github.ref == 'refs/heads/main'로 job을 막는다.
  • 운영 repo 구조: brain 코드는 이 kit와 같은 자리(skills/codebase-brain/)에 둔다. 고정한 커밋에서 복사하고, 운영 repo PR로만 바꾼다. bin/brain은 sh wrapper라 그대로 실행한다(node bin/brain이 아니다). cache 열쇠에 run_attempt를 넣는다. cache는 한 번 저장하면 바뀌지 않고, 재실행은 같은 run_id를 쓰기 때문이다(GitHub caching).
  • 소스 커밋은 github.sha가 아니다. github.sha는 운영 repo의 커밋이다. ci-publish가 git -C src-repo rev-parse HEAD로 읽어 attempt에 쓴다.
  • GITHUB_TOKEN은 다른 비공개 repo를 읽지 못한다. checkout과 GitHub 수집 모두 BRAIN_SOURCE_TOKEN을 쓴다. GITHUB_TOKEN은 이 run의 created_at을 읽는 데만 쓴다(GET /repos/{운영 repo}/actions/runs/{run_id}, Actions read).
  • action은 40자 커밋 SHA로 고정한다(S1에서 실제 값을 넣고 actionlint로 검사). 자격 증명을 checkout에 남기지 않는다.
  • pull_request · pull_request_target trigger는 없다. 운영 repo 설정에서 fork PR에 secret을 보내지 않는다.
  • push마다 돌리려면 on.push.branches: [main]를 더하면 된다. 다만 운영 repo 방식에서는 소스 repo의 push가 운영 repo를 깨우지 못하므로, 소스 repo 쪽에 dispatch를 보내는 장치가 필요하다(§9).
  • brain-bootstrap.yml: 같은 단계에 ci-publish --full --mode bootstrap. 상한을 따로 둔다: job 360분, ci-publish step 350분, S4 sync 상한과 rate limit 대기 상한 없음(요청 하나 30초는 그대로), S5 transaction_timeout=10min · statement_timeout=5min(첫 publish는 행을 전부 넣는다). S3 build 3분은 그대로. A5 건너뛰기는 하지 않는다.
  • bootstrap 게이트: dispatch 토큰의 Actions write는 repo 전체에 걸려, 그 토큰으로 bootstrap도 dispatch할 수 있다. 그래서 job의 첫 step이 repo 변수 BRAIN_BOOTSTRAP_UNTIL(UTC 시각)을 본다. 지금보다 뒤이고 2시간 안일 때만 계속하고, 아니면 DB에 닿기 전에 끝난다. 변수를 바꾸려면 fine-grained 토큰의 Variables write가 필요하고, dispatch 토큰에는 그 권한이 없다(권한 표). 관리자가 gh variable set으로 열고 dispatch한다. environment의 required reviewers는 GitHub Free · Pro · Team의 비공개 repo에서 쓸 수 없어 고르지 않았다(GitHub environments).
      - name: bootstrap gate                   # brain-bootstrap.yml의 첫 step
        env:
          UNTIL: ${{ vars.BRAIN_BOOTSTRAP_UNTIL }}
        run: |
          now=$(date -u +%s); until=$(date -u -d "${UNTIL:-1970-01-01}" +%s) || exit 1
          [ "$until" -gt "$now" ] && [ "$until" -le $((now + 7200)) ] || { echo "bootstrap gate closed"; exit 1; }

6.6 brain refresh (스킬의 자동 갱신)

#규칙근거
F1새로 시작하는 refresh가 이미 fresh(§6.5: code same, memory fresh)를 보면 dispatch도 기다림도 없이 바로 exit 0. 상태 파일이 있는(이어 가는) refresh는 이 지름길을 쓰지 않는다: 시작 때 적은 T와 HEAD를 기준으로 F7의 세 조건을 다 봐야 exit 0이다. 낡음 판정이 refresh 필요일 때만 dispatch한다. activity가 queued · running이면 dispatch하지 않고 기다린다불필요한 run을 만들지 않는다
F2같은 노트북의 refresh끼리는 상태 파일 잠금(F11)으로 dispatch를 하나로 줄인다. 다른 노트북끼리는 막지 못한다. 그래서 job 시작의 건너뛰기(A5)가 실제 publish를 하나로 만든다dispatch API 호출 자체는 원자적으로 막을 수 없다
F3cooldown: 15분 안에 같은 main HEAD로 failed · abandoned가 된 attempt, 또는 failed before start(소스 커밋을 모름)가 있으면 다시 dispatch하지 않는다. exit 1과 마지막 실패를 보고한다실패하는 run을 에이전트가 반복해서 부르지 않게. 시작 전 실패는 소스 커밋이 없어 HEAD와 상관없이 센다

F5dispatch 응답을 못 받으면 다시 보내지 않는다. 진행 중인 run 목록을 보고, 없으면 다음 호출에서 한 번만 다시 보낸다응답 유실로 dispatch가 두 번 가는 일을 줄인다

6.7 보안

  • 에이전트가 할 수 있는 것: brain 읽기(reader), 운영 repo workflow dispatch와 run 상태 읽기(BRAIN_DISPATCH_TOKEN). 할 수 없는 것: brain 쓰기, 운영 repo push, secret 읽기, workflow 수정, 다른 ref로 publish, publish 내용 바꾸기, bootstrap 게이트 열기(repo 변수 쓰기).
  • 경계가 서는 조건: 운영 repo의 쓰기 권한은 관리자만 갖는다. 에이전트가 쓰는 개발자 계정은 운영 repo 협업자가 아니다. 이 조건은 사람의 운영 규칙이라 S7에서 sandbox로 실제로 확인한다(§7.3 P17).
  • 소스 repo에는 brain 비밀이 없다. 소스 repo에 push한 브랜치 workflow가 비밀을 꺼낼 길이 없다.
  • fork PR: 기본값으로 secret이 넘어가지 않는다(GitHub secrets). 비공개 repo의 fork PR secret 설정은 끈다. workflow에 pull_request · pull_request_target이 없다.
  • GITHUB_TOKEN은 contents: read · actions: read만. 수집은 BRAIN_SOURCE_TOKEN(시간당 5,000)이 한다. 평소 증분 run은 약 80 요청이다.
  • 로그와 attempt.error에는 단계 이름과 오류 종류만 쓴다. Phase 2 R16의 검사를 로그에도 돌린다(§7.3 P5).

9. 열린 질문 (리뷰에서 정해 주세요)

  1. push마다 돌릴까? "푸시 한 번에 10분"이 push trigger를 뜻했다면, 운영 repo 방식에서는 소스 repo에 작은 workflow(운영 repo로 dispatch만 보냄)가 필요합니다. 서비스 repo를 건드리는 일이라 이번에는 넣지 않았습니다. 기본안은 "schedule + 요청 dispatch"입니다.
  2. 낡음 기준. 기억은 요구사항대로 24시간입니다. 코드는 "main과 다르면"입니다. refresh가 너무 자주 돌면 "N커밋 이상 또는 2시간 이상"으로 늘릴 수 있습니다.
  3. dispatch 토큰을 누가 갖나. 기본안은 팀 공용 fine-grained 토큰 하나(운영 repo의 Actions 권한만)입니다. 사람마다 만들면 끊기는 쉽지만, 운영 repo 소유자가 토큰마다 승인해야 할 수 있습니다.
  4. 실패 알림. 지금은 footer · brain status · Actions 화면뿐입니다. 연속 2회 실패에 알림(이메일 · Slack)을 원하시면 알려 주세요.

10. 한계

  • GitHub schedule은 늦거나 빠질 수 있다. 빠진 날의 갱신은 다음 질문의 refresh에 기댄다. 아무도 묻지 않으면 그날은 낡은 채로 있고 footer가 그렇게 말한다.
  • 전부 아니면 전무라서, GitHub API가 오래 실패하면 지도도 갱신되지 않는다. 지도만 먼저 쓰는 길은 요구사항 때문에 열지 않았다.
  • 여러 노트북에서 동시에 refresh하면 dispatch가 두 번 갈 수 있다. publish는 job 시작의 건너뛰기로 한 번이 된다.
  • 경계는 "운영 repo에 관리자만 push한다"는 운영 규칙에 기댄다. 이 규칙이 깨지면 writer 비밀도 지켜지지 않는다.
  • dispatch 토큰이 없는 사람의 에이전트는 낡았다고 말만 한다.
  • 에이전트 도구의 명령 시간 상한이 90초보다 짧은 환경이면 한 번 호출의 기다림을 줄여야 한다(BRAIN_REFRESH_CALL_S).
  • force-push 뒤에는 관리자가 게이트를 열고 brain-bootstrap을 한 번 돌려야 한다. 그때까지 평소 publish는 멈춘다.
  • 실패 주입은 프로그램 안의 훅과 테스트 proxy다. 바깥 장비 고장은 연결 끊기와 응답 버리기로만 흉내 낸다.
